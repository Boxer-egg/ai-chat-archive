## 0. 一页看懂（给产品经理）

**一句话**：装一个只在 AI 对话页面上工作的浏览器扩展，把对话内容抄一份到你自己电脑的本地数据库里。不上传、不注册、不依赖任何服务器。

**四个关键取舍**

| 问题 | 我们的做法 | 为什么 |
| --- | --- | --- |
| 数据放哪 | 浏览器自带的 IndexedDB（本地数据库） | 容量大（几百 MB 级）、不用服务器、断网可用 |
| 怎么认出同一条消息 | 优先用平台自己的消息 ID；没有就用"角色 + 内容指纹" | 刷新、重新生成、多标签页同时开，都不会重复 |
| 平台改版了怎么办 | 每个平台一个独立"适配器"小文件，坏了只修那一个 | 不会一个平台改版拖垮全部 |
| 多账号怎么区分 | 每个账号一份独立归档；Chrome 不同配置文件天然隔离 | 换号不会串数据，导出也不会混在一起 |

**你会看到的四个界面**

1. 扩展图标上的小角标：绿色 = 正在保存（数字为已存条数）；灰色 = 当前站点不支持或已暂停；橙色 `!` = 适配失败，需要手动同步或等更新。
2. 点开图标的弹窗：本站是否支持、当前账号、已保存多少条、最近同步时间、自动保存开关、暂停本站、手动同步按钮。
3. 归档页：会话列表 + 详情 + 搜索（按标题、内容、平台、日期）。
4. 设置页：导出 / 导入 / 清空 / 排除站点 / 调试日志。

**工期**：单人开发，先做 2 个平台的可验证版本约 2–3 周；补齐 5 个平台再加约 2–3 周，合计约 4–5 周。详见第 15 章。

**三个主要风险（以及我们的兜底）**

- 平台 DOM 经常改版 → 适配器独立 + 自检 + 失败可见 + 手动同步兜底。
- 页面只渲染一部分历史（虚拟列表）→ 不硬闯，用户滚动到哪就采到哪，并提示"继续向上滚动"。
- 后台进程随时可能被浏览器休眠 → 所有写入设计成"重复执行也安全"，中断就重试。

## 1. 范围与非目标

### 1.1 本期范围

- 支持 DeepSeek、Kimi、Claude、ChatGPT、Grok 五个平台的对话页（仅 Chrome 桌面版）。
- 只归档用户与助手的可见文本和代码块；system / tool 内容、Artifacts 面板不采集。
- 图片与附件只保存 URL 与文件名，不下载文件本体（后续版本再加"保存副本/下载链接"选项）。
- 自动保存用户消息与 AI 回复；追加、更新、历史补录、标题同步。
- 本地会话列表、详情、搜索、导出（默认 Markdown，JSON 作为备份）、导入恢复、清空。
- 自动保存开关、按站点暂停/排除、适配失败提示、调试日志。

### 1.2 明确不做（避免范围蔓延）

- 不做云同步、账号体系、任何形式的数据上传。
- 不修改平台页面内容，不接管发送/编辑行为，只读。
- 不下载附件或图片本体，只保留 URL 与文件名。
- 不绕过平台的虚拟列表或付费限制去"强行"拉取未渲染的消息。
- 不做移动端浏览器；只支持 Chrome 桌面版，Firefox / Edge 不测试、不适配。
- 不做无痕（Incognito）窗口归档：扩展不在无痕模式运行。
- 不做"在归档页里继续对话"，归档就是只读备份。

### 2.2 一条消息的完整路径

1. 用户在页面发消息 → 消息容器 DOM 变化 → `MutationObserver` 触发。
2. 800ms 防抖后（流式期间改为节流，见 6.6），`extractor` 调 adapter 扫描当前消息节点，产出 `RawMessage[]` + 会话标识 + 标题 + 账号线索。账号线索在本地算成 `accountKey`，不把原始标识发出去。
3. 内容脚本检查开关（全局 / 站点 / 排除列表），命中则发 `UPSERT_SNAPSHOT`（携带 `accountKey`、`conversationId`、`title`、`raws`）。
4. Service Worker 按 `conversationId` 进入串行队列，读取该会话已有消息。
5. merge 引擎对齐、去重、计算顺序，生成"新增 / 更新 / 忽略"三组变更。
6. 单个 IndexedDB 事务提交（必要时分块），返回 `{ inserted, updated, skipped, messageCount }`。
7. SW 更新角标，通过 `BroadcastChannel` 通知已打开的归档页/其他标签页刷新。
8. 内容脚本收到回执后更新"本次已保存"的指纹缓存，避免同一内容反复提交。

### 2.3 为什么由 Service Worker 单点写库

- 多个标签页同时打开同一会话时，写入天然串行，不靠跨标签页锁。
- 归档页只读，避免 UI 与采集竞争。
- SW 被休眠不会丢数据：写入是幂等的，内容脚本拿不到回执会退避重试；事务本身要么全成要么全败。

**MV3 生命周期处理**：SW 不持有"必须活着"的假设。每次收到消息先 `ensureReady()`（打开数据库、加载设置，结果缓存），30 秒内完成；不在内存里存半成品状态；长任务拆成多个事务并记录断点（会话级 `syncState`）。

### 2.4 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript（strict） | 消息协议、适配器接口需要类型约束 |
| 构建 | Vite + `@crxjs/vite-plugin` | MV3 原生支持、HMR、多入口；备选 WXT |
| UI | Preact + 原生 CSS（不引 UI 框架） | 包体小，扩展不需要复杂组件库 |
| 存储 | IndexedDB（原生封装，不引 Dexie） | 需要精确控制事务与迁移；封装层约 300 行 |
| HTML 清洗 | DOMPurify（本地打包） | 存 HTML 前必须消毒，防止归档页 XSS |
| 测试 | Vitest + fake-indexeddb + Playwright | 单元 / 集成 / 端到端三层 |
| 代码规范 | ESLint + Prettier，禁止 `fetch` 等网络 API（自定义规则） | 用构建期约束保证"零上传" |

## 4. 平台适配器

### 4.1 职责边界

适配器只回答七个问题：**这是不是会话页、会话 ID 是什么、当前是哪个账号、标题是什么、消息在哪、这条消息是什么、现在是不是还在生成**。去重、排序、写库、开关、重试全部由核心层负责。这样平台改版时，改动被限制在一个文件里。

### 4.2 接口定义（可直接落地的契约）

```ts
// src/content/adapters/types.ts
export type PlatformId = 'deepseek' | 'kimi' | 'claude' | 'chatgpt' | 'grok';
// 采集只产出 user / assistant；system / tool 预留给导入的第三方备份
export type Role = 'user' | 'assistant' | 'system' | 'tool';
export type CapturedRole = Extract<Role, 'user' | 'assistant'>;

export interface AdapterContext {
  url: URL;
  document: Document;
  /** 平台刚切换会话时的短暂不稳定的规避用，由 bootstrap 传入 */
  now: number;
}

export interface ConversationRef {
  platformConversationId: string;
  /** 记录来源，排障用：URL 里的 UUID / DOM 的 data-* / 兜底生成 */
  source: 'url' | 'dom' | 'generated';
}

export interface RawMessage {
  /** 平台自己的消息 ID（有就一定要给，这是去重第一优先级） */
  platformMessageId?: string;
  role: Role;
  /** 纯文本，必须保留换行与代码缩进 */
  text: string;
  /** 已消毒的 HTML（可选，用于保留代码块/列表格式） */
  html?: string;
  /** 本次扫描中的 DOM 顺序，仅用于对齐与排序，不做身份标识 */
  domIndex: number;
  /** 这条消息当前是否还在流式输出 */
  streaming?: boolean;
  /** 平台提供的时间戳（毫秒），没有就留空 */
  timestamp?: number;
  /** 只存 URL 与文件名，不下载本体 */
  attachments?: Array<{ type: 'image' | 'file' | 'link'; name?: string; url?: string }>;
}

/** 账号线索：只从页面可见信息里取，绝不读 Cookie / localStorage / 登录令牌 */
export interface AccountHintInput {
  /** 平台内稳定的原始标识（用户 ID、邮箱、workspace/组织 ID）。只在本机内存里短暂存在 */
  rawId: string;
  /** 给人看的展示名，核心层负责脱敏后再落库 */
  label: string;
  source: 'dom-id' | 'email' | 'workspace' | 'avatar';
}

export interface AdapterDiagnosis {
  status: 'ok' | 'degraded' | 'broken';
  messageCount: number;
  /** 哪些选择器/步骤没命中，写进状态面板和调试日志 */
  misses: string[];
  notes?: string;
}

export interface PlatformAdapter {
  readonly id: PlatformId;
  /** 适配器版本，写进每条消息，便于回溯"这条是哪版选择器采集的" */
  readonly version: string;
  readonly displayName: string;
  /** 仅用于开发期校验与 manifest 生成，运行时以 manifest 为准 */
  readonly hosts: string[];

  /** 是否接管这个 URL（不含无关的登录页/设置页） */
  match(url: URL): boolean;

  /** 会话标识；返回 null 表示"当前不是会话页"（例如新会话还没生成 URL） */
  getConversation(ctx: AdapterContext): ConversationRef | null;

  /**
   * 当前登录账号的线索。拿不到返回 null，核心层归入"默认账号"。
   * 只允许读页面可见信息；禁止读 Cookie、localStorage、sessionStorage、IndexedDB。
   */
  getAccountHint(ctx: AdapterContext): AccountHintInput | null;

  /** 标题；页面未渲染完成时允许返回 null */
  getTitle(ctx: AdapterContext): string | null;

  /** 消息列表容器：MutationObserver 只观察它，绝不 observe(document.body) */
  getMessageRoot(ctx: AdapterContext): Element | null;

  /** 按 DOM 顺序返回消息节点（只返回"消息"这一层的节点） */
  getMessageNodes(ctx: AdapterContext): Element[];

  /** 解析单条消息；解析失败返回 null，由核心层计入 misses，不抛异常 */
  parseMessage(node: Element, ctx: AdapterContext): RawMessage | null;

  /** 是否正在生成（用于决定草稿节流与完成时机） */
  isStreaming(ctx: AdapterContext): boolean;

  /** 滚动容器；用于监听"向上加载历史"并触发补录 */
  getScrollContainer(ctx: AdapterContext): HTMLElement | null;

  /** 可选：平台自己的"加载更多"触发元素，用于更早地感知 */
  getLoadMoreTrigger?(ctx: AdapterContext): Element | null;

  /** 自检：给状态面板/调试面板用 */
  diagnose(ctx: AdapterContext): AdapterDiagnosis;
}
```

### 4.3 选择器配置化（不写死）

每个适配器内部用"候选选择器"描述，按顺序尝试，命中即用；全部落空时记录 `misses`，**不抛错、不影响页面**。

```ts
// src/content/adapters/selectors.ts
export interface SelectorSpec {
  name: string;            // 语义名，日志里用，例如 'message-node'
  selectors: string[];     // 从最稳到最不稳，按顺序尝试
  required?: boolean;      // required 全部失败 → diagnose 至少 degraded
}

export function pick(
  root: ParentNode,
  spec: SelectorSpec,
  misses: string[],
): Element | null {
  for (const sel of spec.selectors) {
    try {
      const el = root.querySelector(sel);
      if (el) return el;
    } catch { /* 无效选择器不应让整页失效 */ }
  }
  misses.push(spec.name);
  return null;
}
```

选择器优先级（按稳定性从高到低）：

1. 语义属性：`data-testid`、`data-message-author-role`、`aria-label`、`role="article"`、`data-*` 业务字段。
2. 结构锚点：消息列表的 `main` / `[role="log"]`，以及"用户气泡 vs 助手气泡"的相对位置。
3. 稳定 class 片段（如 `markdown`、`prose`）。
4. 最后才考虑带哈希的 class（例如 `._9663006`）——这类必须有注释标明"易失效，仅兜底"。

**硬性规则**：任何选择器不得出现在 `content/adapters/` 以外；每个选择器必须带一行注释说明"依据什么 DOM 特征、验证日期、失效后的替代方案"。

### 4.5 自检与降级

内容脚本在以下时机跑 `diagnose()`：

- 页面加载完成后 3 秒；
- URL 变化（SPA 切换会话）后 1.5 秒；
- 每次成功/失败提取后（失败才上报，避免刷日志）。

判定规则：

| 现象 | 判定 | 展示 |
| --- | --- | --- |
| 是会话页，能拿到会话 ID，消息节点 ≥ 1，解析成功率 100% | ok | 绿色角标 |
| 消息节点 ≥ 1，但有节点解析失败，或标题/滚动容器拿不到 | degraded | 黄色角标 + 弹窗提示"部分内容未能保存" |
| 是会话页但消息节点为 0（且页面明显有消息），或连续 3 次提取异常 | broken | 橙色 `!` + 弹窗"当前页面无法自动保存，可点手动同步或等待适配更新" |

**降级策略**：

1. broken 时停止自动写入定时器，避免无效开销，但保留手动同步按钮。
2. 不隐藏错误，也不弹 `alert`；只在扩展角标与弹窗里提示，页面本身零干扰。
3. 用户点"手动同步"时，即使 degraded 也强制跑一次完整扫描，并把诊断结果写进调试日志。

### 4.6 新增一个平台的步骤（写进 adapter-guide.md）

1. 复制 `adapters/base.ts` 的骨架，新建 `adapters/<id>.ts`。
2. 填 `hosts` / `match` / `getConversation`（先解决 URL 里的 ID）。
3. 用真实页面保存 2 份 HTML 夹具（新会话 3 轮、长会话 50 条以上），放进 `tests/integration/fixtures/<id>/`；另存一份"已登录账号菜单"的 DOM 片段，用于 `getAccountHint`。
4. 对着夹具写 `getMessageNodes` / `parseMessage`，跑集成测试到全绿。
5. 在 `registry.ts` 注册，在 `manifest.ts` 加域名，跑 `diagnose` 冒烟。
6. 在真机上手工过一遍第 16 章的验收清单。

## 5. 数据模型与 IndexedDB

### 5.1 为什么不用 `chrome.storage`

`chrome.storage.local` 的配额（默认 10MB，申请 `unlimitedStorage` 后可放大）足够存几万条文本，但它只能整块读写、没有索引、没有事务，搜索和排序都要全量加载。IndexedDB 有索引、有事务、容量按磁盘配额走，才撑得住"跨平台归档 + 搜索"。设置项仍放 `chrome.storage.local`（同步方便、体积小），对话数据放 IndexedDB。

### 5.2 数据库定义

- 数据库名：`ai-chat-archive`
- 当前版本：`1`（后续每次结构变化 +1）
- 连接方：SW（读写）、归档页（只读）、搜索 Worker（只读）

| Store | keyPath | 索引 | 说明 |
| --- | --- | --- | --- |
| `conversations` | `id` | `by_platform(platform)`、`by_account(accountKey)`、`by_updatedAt(updatedAt)`、`by_platform_account_pcid(platform, accountKey, platformConversationId)` **unique**、`by_url(url)` | 一个会话一条；`id = platform:accountKey:pcid` |
| `accounts` | `id` | `by_platform(platform)`、`by_lastSeenAt(lastSeenAt)` | 账号/工作区档案；只存脱敏展示名 |
| `messages` | `id` | `by_conv_order(conversationId, order)`、`by_conv_key(conversationId, msgKey)` **unique**、`by_conv_hash(conversationId, contentHash)`、`by_conv_status(conversationId, status)`、`by_savedAt(savedAt)` | 一条消息一条 |
| `settings` | `key` | — | 开关、排除站点、调试标记 |
| `events` | `id` (autoIncrement) | `by_ts(ts)` | 诊断事件环形缓冲，上限 500 条 |
| `meta` | `key` | — | `schemaVersion`、`installId`、`lastMaintenanceAt` |
| `syncState` | `conversationId` | — | 断点与最近一次同步结果（用于重试与提示） |

### 5.3 记录结构

```ts
interface Conversation {
  id: string;                       // `${platform}:${accountKey}:${platformConversationId}`
  platform: PlatformId;
  accountKey: string;               // 账号键（稳定哈希），见 8.4
  accountLabel: string;             // 脱敏展示名，如 a***@gmail.com / 团队工作区
  platformConversationId: string;
  title: string;
  url: string;                      // 最近一次采集时的完整 URL
  createdAt: number;
  updatedAt: number;                // 最后一条消息的时间（展示排序用）
  lastSyncedAt: number;             // 最后一次成功写入时间
  messageCount: number;             // 完整消息数（不含 draft）
  adapterVersion: string;
  source: 'url' | 'dom' | 'generated';
  /** 同会话出现过不同 URL 时保留历史，便于跳转与排障 */
  urlHistory: string[];
}

interface Account {
  id: string;                       // `${platform}:${accountKey}`
  platform: PlatformId;
  accountKey: string;
  label: string;                    // 脱敏展示名
  source: 'dom-id' | 'email' | 'workspace' | 'avatar' | 'default';
  firstSeenAt: number;
  lastSeenAt: number;
}

interface Message {
  id: string;                       // `${conversationId}#${msgKey}`（确定性，天然幂等）
  conversationId: string;
  msgKey: string;                   // 去重身份键，见 6.1
  platformMessageId?: string;
  role: Role;
  contentText: string;
  contentHtml?: string;             // 已消毒
  markdown?: string;                // MVP 留空，导出时由 HTML 转换
  order: number;                    // 展示顺序，浮点，见 7.4
  timestamp?: number;               // 平台时间
  fingerprint: string;              // 内容指纹，见 6.2
  contentHash: string;              // 规范化文本的 SHA-256（短截）
  status: 'draft' | 'complete';
  truncated?: boolean;              // 超长被截断/生成被中断
  domIndex?: number;                // 最近一次看到的位置，仅调试用
  savedAt: number;
  updatedAt: number;
  adapterVersion: string;
}

interface SyncState {
  conversationId: string;
  lastAttemptAt: number;
  lastResult: 'ok' | 'partial' | 'error';
  lastError?: string;
  /** 最近一次成功写入的完整指纹集合哈希，用于快速判断"没有变化" */
  snapshotHash: string;
}
```

**为什么 `message.id` 是确定性拼接**：`put()` 天然幂等，多标签页、重试、SW 重启都不会产生第二行；配合 `by_conv_key` 唯一索引，即使两条并发写入也只会有一条成功，另一条被 `ConstraintError` 拦下并按"已存在"处理。

### 5.4 迁移机制

```ts
// src/core/db/open.ts
const MIGRATIONS = [migrateV1]; // 下标 0 → version 1

export async function openDB(): Promise<IDBDatabase> {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open(DB_NAME, DB_VERSION);
    req.onupgradeneeded = (e) => {
      const db = req.result;
      const from = e.oldVersion;
      for (let v = from; v < DB_VERSION; v++) MIGRATIONS[v]?.(db, req.transaction!);
    };
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
    req.onblocked = () => reject(new Error('DB blocked by another tab'));
  });
}
```

规则：

- 只在 `onupgradeneeded` 里改结构；数据迁移（字段补齐、重算 `msgKey`）也用同一事务，保证原子。
- 升级前把 `schemaVersion` 写进 `meta`，导出文件也带 `schemaVersion`，导入时拒绝"高版本文件导入低版本扩展"。
- 不删旧字段，先加新字段并双写，下一个版本再清理（避免回滚丢数据）。
- 迁移必须有单测：造 v1 数据 → 升到 v2 → 断言消息数、顺序、索引都正确。
- v1 初版就包含 `accountKey`（见 §8.4），不需要为多账号做额外的历史数据回填；后续若调整账号键算法，才需要写迁移。

### 5.5 容量与写入策略

- 单条消息文本上限 256KB，超出截断并标 `truncated: true`（极少见，主要是超长代码/日志）。
- HTML 与文本分开存，但都放在同一条记录里；单条记录超过 1MB 概率极低，可接受。
- 写入按 200 条一个事务分块；顺序号在内存里一次算好，分块只影响提交次数，不影响最终一致性。
- 每 24 小时做一次轻量维护（`alarms`）：统计用量、检查配额、写入 `lastMaintenanceAt`；**不自动删除任何数据**（保留策略为永久，只有用户主动删除时才清理）。
- 未完成的 draft 不自动清理，也不计入消息数；下次看到同一条消息时会被覆盖为 complete，长期未完成的在详情页显示"未完成"标记。
- 容量告警：`navigator.storage.estimate()` 使用率超过 80% 时在弹窗提示导出备份。

## 6. 去重与幂等

### 6.1 消息身份键 `msgKey`

```
有平台消息 ID：  msgKey = `p:${platformMessageId}`
否则：          msgKey = `f:${fingerprint}`  + 重复序号后缀（见 6.3）
```

`message.id = conversationId + '#' + msgKey`，所以同一条消息无论被采集多少次，落库位置只有一个。

### 6.2 内容指纹

```ts
export function normalize(text: string): string {
  return text
    .replace(/\u200b|\u200c|\u200d|\ufeff/g, '') // 零宽字符
    .replace(/\r\n?/g, '\n')
    .replace(/[ \t]+$/gm, '')                    // 行尾空白
    .replace(/\n{3,}/g, '\n\n')                  // 连续空行
    .trim();
}

export async function fingerprint(role: Role, text: string): Promise<string> {
  const data = `${role}\u0000${normalize(text)}`;
  const buf = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(data));
  return [...new Uint8Array(buf)].slice(0, 8)
    .map((b) => b.toString(16).padStart(2, '0')).join('');
}
```

注意：

- **不做**大小写折叠、标点删除——那会让"同一句话改了个标点"被当成同一条，丢失编辑。
- 代码块内部的缩进不压缩，只去行尾空白，保证内容哈希对代码敏感。
- 指纹只用于"没有平台 ID"的兜底，不作为唯一真相。

### 6.3 去重优先级

严格按需求给的顺序，逐级回退：

| 级别 | 匹配键 | 适用场景 | 命中后行为 |
| --- | --- | --- | --- |
| 1 | `platformMessageId` | 平台在 DOM 上暴露消息 ID | 同 ID → 比对 `contentHash`，不同则更新，不新增 |
| 2 | `role + domIndex + contentHash` | 平台无 ID，但列表稳定、只是重渲染 | 位置与角色都对得上且内容一致 → 视为同一条，刷新 `domIndex` |
| 3 | `fingerprint`（角色 + 规范化文本） | 平台无 ID，且位置会变（如历史插入） | 命中 → 比对哈希；重复文本按出现序号消歧 |
| 4 | 都不中 | 确实是新消息，或内容被大改 | 新增；若同位置同角色且相似度高，转为"更新"而非新增（见 7.3） |

**重复文本的消歧**：同一会话里用户可能发多次"继续"。规则是——按本次扫描中的出现次序，给同指纹的消息依次分配 `#1`、`#2`……与库中同指纹消息按 `order` 排序后一一对应；多出来的才新增。这样"连续发三条 继续"不会被合并成一条，也不会每次刷新都新增三条。

```ts
// 伪代码：单条消息的匹配
function matchMessage(raw: RawMessage, ctx: MatchContext): Match {
  if (raw.platformMessageId && ctx.byPlatformId.has(raw.platformMessageId))
    return { kind: 'update', target: ctx.byPlatformId.get(raw.platformMessageId)! };

  if (ctx.byDomIndex.has(raw.domIndex)) {
    const m = ctx.byDomIndex.get(raw.domIndex)!;
    if (m.role === raw.role && m.contentHash === ctx.hash(raw))
      return { kind: 'touch', target: m };   // 位置+角色+内容都对上
    if (m.role === raw.role)
      return { kind: 'update', target: m };  // 同位置同角色但内容变了（编辑/重生成）
  }

  const key = ctx.fingerprint(raw);
  const candidates = ctx.byFingerprint.get(key) ?? [];
  const used = ctx.consumed.get(key) ?? 0;
  if (used < candidates.length)
    return { kind: 'touch', target: candidates[used] };

  return { kind: 'insert' };
}
```

> 说明：级别 2 只在"本次是完整快照（消息节点数 ≥ 已知数量）"且 diff 未发现大规模位移时启用；否则直接走级别 3，避免历史插入导致错位更新。

### 6.4 多标签页并发

三层保护，任意一层单独都能兜住：

1. **单写者**：只有 SW 写库；SW 内部按 `conversationId` 维护 `Promise` 链，同一会话的合并串行执行。
2. **事务内读改写**：`readwrite` 事务里先读后写，IndexedDB 对同一 store 的读写事务串行，天然避免"两个都判断不存在然后各插一条"。
3. **唯一索引兜底**：`by_conv_key(conversationId, msgKey)` 唯一；并发冲突时捕获 `ConstraintError`，回退为"读取现有记录 + 更新"，不报错给用户。

跨标签页不需要加锁，因为同一会话的两次快照内容相同，合并是幂等的；内容不同（一个标签页在编辑）时，后到的快照按 `updatedAt` 后写覆盖，并在 `syncState` 记一条 `conflict` 事件供排查。

### 6.5 编辑与重新生成

- 有平台 ID：直接按 ID 更新 `contentText/contentHash/updatedAt`，`order` 不变。
- 无平台 ID：走级别 3 匹配；若指纹对不上但"同一位置 + 同角色 + 文本相似度 ≥ 0.6"，判为编辑，更新原记录并保留 `editedAt`。
- 重新生成会产生"同一条消息的新内容"，多数平台会换 DOM 节点但位置不变，因此级别 2 能命中；若平台换了 ID，则旧记录保留、新记录新增，并在会话里标记"存在同位置多版本"（MVP 不做版本树，只保留最新一条 + `previousContentHash` 便于排查）。
- 用户删除网页上的消息：**不主动删除本地记录**（归档是"见过就留"），但在详情页可手动删除单条。

### 6.6 流式草稿

| 阶段 | 行为 |
| --- | --- |
| 首次出现流式内容 | 400ms 后写一条 `status: 'draft'` |
| 生成中 | 节流：每 1500ms 且文本变化 ≥ 20 字符才写；单次写入只更新这一条 |
| 完成判定 | `isStreaming() === false` 且文本 1200ms 未变化 → 写 `status: 'complete'`，计算最终 `contentHash`，更新 `messageCount` |
| 页面隐藏/关闭 | `visibilitychange` 时强制 flush 一次草稿（不等待回执） |
| 生成被中断 | 保留已有内容，`status: 'complete'`，`truncated: true` |

草稿不计入 `messageCount`，搜索默认过滤 draft，避免"半句话"污染结果。

## 7. 历史补录与顺序合并

### 7.1 要解决的问题

页面初始只渲染最新 20 条，用户向上滚动加载出 50 条更早的消息。这 50 条要插到已有 20 条**前面**，不能追加到末尾；同时这 50 条里可能包含与已有记录重叠的消息，不能重复。

### 7.2 算法总览（四步）

```
输入：conversationId、本次扫描到的 RawMessage[]（DOM 顺序）、已有的 Message[]（按 order 排序）
输出：inserts / updates / touches / 新的完整顺序

① 预处理：规范化 → 计算 contentHash / fingerprint → 有平台 ID 的建 map
② 对齐：把「已有消息的内容哈希序列」与「本次扫描的哈希序列」做 Myers diff，
        得到匹配块（同一条消息）、插入块（新消息）、删除块（未渲染/被删）
③ 决策：匹配块 → touch/update；插入块 → 按锚点插入；未匹配的旧消息 → 保留原位
④ 排序：新消息用小数序号插到锚点之间；精度耗尽才整段重排
```

### 7.3 对齐（Myers diff）

- 序列元素是 `contentHash`，不是文本，比较是 O(1)。
- 用 Myers 算法（与 git diff 同源），复杂度 O((N+M)·D)，D 是差异量；正常情况 D 很小，几百条消息毫秒级。
- 上限保护：单次参与对齐的消息数 ≤ 4000；超过则退化为"只对最后 4000 条做 diff + 其余按指纹匹配"，避免长会话卡顿。
- 对齐结果里，"同一条消息"的判定仍然服从 6.3 的优先级：先平台 ID 精确匹配，再用 diff 的匹配块，最后用指纹。

**为什么用 diff 而不是简单按位置**：历史插入会让所有位置后移，按位置会把 50 条全判成"内容变了"从而触发 50 次更新甚至误新增；diff 能识别出"前面插了一段、后面的内容整体平移"，只把真正的新消息标为 insert。

### 7.4 顺序号（order）

- 初始分配：第 i 条 `order = (i + 1) * 1024`（留空隙）。
- 插到 a、b 之间：`order = (a + b) / 2`；插到最前：`a - 1024`；插到最后：`b + 1024`。
- 浮点数在 double 精度下，同一位置最多连续插约 50 次才会耗尽；耗尽时把该会话所有消息按当前顺序重排为 `(i+1)*1024`（一次事务，几千条毫秒级）。
- `order` 只表示顺序，不参与身份判断，所以重排不会影响去重。

### 7.5 合并过程（伪代码）

```ts
async function mergeSnapshot(convId: string, raws: RawMessage[]): Promise<MergeResult> {
  const existing = await messagesRepo.listByConversation(convId); // 已按 order 排序
  const ctx = buildMatchContext(existing, raws);                  // map: platformId / domIndex / fingerprint

  // 1) 精确匹配（平台 ID / 位置+角色+哈希）
  const matched = new Map<number, Message>();      // rawIndex -> existing
  const rest: number[] = [];
  raws.forEach((raw, i) => {
    const m = matchExact(raw, ctx);
    if (m) matched.set(i, m); else rest.push(i);
  });

  // 2) 对剩余部分做 diff，找出插入块与"位置平移"
  const aligned = alignByContentHash(existing, raws, matched);

  // 3) 逐个落位
  const inserts: Message[] = [];
  const updates: Message[] = [];
  for (let i = 0; i < raws.length; i++) {
    const raw = raws[i];
    const hit = aligned.matchOf(i);
    if (hit) {
      if (hit.contentHash !== contentHash(raw)) updates.push(toUpdate(hit, raw));
      else touch(hit, raw);                        // 只更新 domIndex/savedAt
      continue;
    }
    const prev = nearestMatchedBefore(i, aligned);  // 前一个已确认的锚点
    const next = nearestMatchedAfter(i, aligned);   // 后一个已确认的锚点
    inserts.push(toInsert(raw, orderBetween(prev?.order, next?.order), convId));
  }

  // 4) 一个事务提交
  return db.tx(['messages', 'conversations', 'syncState'], 'readwrite', async (tx) => {
    await messagesRepo.bulkPut(tx, [...inserts, ...updates], { chunk: 200 });
    await conversationsRepo.recount(tx, convId);    // 重算 messageCount / updatedAt / lastSyncedAt
    await syncStateRepo.record(tx, convId, { lastResult: 'ok' });
    return { inserted: inserts.length, updated: updates.length, messageCount: await count(tx, convId) };
  });
}
```

### 7.6 边界情况

| 情况 | 处理 |
| --- | --- |
| 历史插到最前 | 用 `first.order - 1024` 递减，必要时重排 |
| 新旧消息交错出现（折叠/展开） | 以 DOM 顺序为准，锚点插值；未渲染的旧消息保留原位 |
| 同一条消息在 DOM 出现两次（引用/预览） | `getMessageNodes` 只取消息列表层；重复节点按 `msgKey` 去重，保留第一次出现的位置 |
| 平台删除了消息 | 不删本地，只记录 `missingInDom: true`（下个版本再加字段，MVP 只记事件） |
| 虚拟列表只渲染窗口内几条 | 以滚动容器可视区为准，采当前窗口；提示"继续向上滚动可补录更多"；不承诺一次拿全 |
| 连续滚动触发多次 | 800ms 防抖 + 同一会话合并队列；同一事务内多次快照自然合并 |
| 页面切换会话 | URL 变化 → `bootstrap` 重建上下文，旧会话的待提交快照先 flush 再切换 |
| 消息数 > 4000 | 只 diff 尾部窗口，其余按指纹匹配，并在 `syncState` 标注 `partial` |

### 7.7 复杂度与预算

| 场景 | 消息数 | 预期耗时 |
| --- | --- | --- |
| 3 轮新会话全量快照 | 6 | < 10ms |
| 追加 1 轮 | 7（与 6 对齐） | < 10ms |
| 补录 50 条历史（总计 70） | 70 | < 30ms |
| 长会话补录（总计 2000） | 2000 | < 200ms（含写库） |
| 极端（总计 8000，只 diff 尾窗） | 4000 参与 | < 500ms |

## 8. 会话识别与标题同步

### 8.1 会话 ID 解析优先级

1. URL 路径/查询中的平台 ID（UUID、数字 ID、短哈希）——**首选**。
2. DOM 上的 `data-conversation-id` / `data-thread-id` / `data-session-id` 等业务属性。
3. 页面内"分享链接""复制链接"按钮的 href。
4. 兜底：首次采集时用 `platform + 建库时间 + 首条消息指纹` 生成稳定 ID，标记 `source: 'generated'`；该会话后续一旦拿到真实 URL，做一次"ID 归并"（把 generated 会话的消息迁移到真实 ID 下，删旧记录）。

**新会话**：刚点"新建对话"时 URL 往往还没有 ID，此时不创建归档；等 URL 出现 ID 后的第一次快照再建库，避免产生一堆空会话。

### 8.2 标题同步

- 标题来源：会话列表高亮项的文本 / 页面顶部标题 / `document.title`（去掉平台后缀）。按此顺序取第一个非空值。
- 防抖 800ms；只有 `title !== conversation.title` 才写，且**只更新标题字段**，不动 `messageCount`、不动消息。
- 生成过程中平台可能先把标题设成"新对话"再改成真实标题，防抖天然过滤掉中间态；额外规则：忽略长度 < 2 或等于平台默认占位文案（"New chat"、"新对话"、"Untitled"）的标题，除非会话已有正式标题。
- 用户手动改名后，本地立即更新；若平台稍后回写旧标题（少见），以最后一次用户可见的标题为准，并记录事件。
- 标题更新与消息写入在同一个会话队列里串行，避免"先写消息后写标题"导致的计数抖动。

### 8.3 会话合并（同平台 ID 不同 URL）

同一会话可能出现 `?from=share`、`#message-xxx` 等变体。规则：`platform + accountKey + platformConversationId` 相同即视为同一会话；把新 URL 追加进 `urlHistory`，主 `url` 更新为不带锚点/追踪参数的规范形式。

### 8.4 多账号与工作区隔离

**结论：账号是归档的第一级维度，不是事后打的标签。** 会话主键为 `platform:accountKey:platformConversationId`，消息、标题、搜索、导出全部继承这个作用域，从数据模型上杜绝串号。

#### 8.4.1 四层处理

**第一层：Chrome 配置文件天然隔离（推荐给"必须严格分开"的用户）**

扩展的 IndexedDB 存在当前 Chrome 配置文件的目录里（macOS 示例）：

```
~/Library/Application Support/Google/Chrome/Default/IndexedDB/chrome-extension_<扩展ID>_0.indexeddb.leveldb
```

不同 Chrome 配置文件（Profile 1 / Profile 2 / 工作资料）各有一份，互相不可见；访客模式、无痕模式也不共享。设置页会明确建议："如果两个账号的数据必须彻底分开，最稳的方式是一号一个 Chrome 配置文件。"这不是代码功能，但它是成本最低、隔离最彻底的方案，必须写进使用说明。

**第二层：同一配置文件内，用"账号指纹"分桶**

- 每个 adapter 实现 `getAccountHint()`，从**页面可见信息**里取账号线索：账号菜单里的邮箱/手机号、设置页的用户 ID、头像菜单、workspace 名称。
- 核心层计算：`accountKey = sha256('ai-archive\0' + platform + '\0' + rawId).slice(0, 12)`。
- `rawId` 只在内存中短暂存在，**不落库、不导出**；落库的是 `accountKey` 和脱敏后的 `label`。
- 脱敏规则：邮箱保留首字符与域名（`a***@gmail.com`）；手机号保留前 3 后 4（`138****8000`）；工作区/组织名原样保留（本身就是公开名称）；昵称保留首尾各 1 字。
- **故意不加随机盐**：加盐会导致"换一台电脑导入备份后，同一账号算出不同的 key"，从而分裂成两个账号桶。哈希只用于去重与隔离，导出文件本身已包含全部对话内容，因此"邮箱哈希可被枚举"不构成额外泄漏。这一点在隐私说明里如实写出。

**第三层：工作区/组织算身份的一部分**

ChatGPT 的"个人 / 团队"、Claude 的多 workspace、企业组织 ID，都参与 `rawId` 计算。同一个邮箱在两个工作区里是**两个桶**——因为会话列表本来就不同，混在一起会串数据。

**第四层：切换检测**

- 触发时机：内容脚本启动、SPA 路由变化、每次快照、`visibilitychange`；结果缓存 5 秒，避免频繁查 DOM。
- 检测到 `accountKey` 变化 → 先把当前待提交快照 flush 到旧账号 → 清空当前会话上下文 → 用新账号重建 → 之后的写入进入新桶。
- 弹窗实时显示"当前账号：a***@gmail.com（团队工作区）"；切换时角标短暂变为蓝色并提示"已切换账号"。
- 账号菜单通常是懒渲染的：页面加载后 3 秒内取不到就重试一次；仍取不到则归入 `default`。

#### 8.4.2 识别不到账号时

`accountKey = 'default'`，`label = '默认账号'`，状态面板提示："未识别到登录账号，已归入默认归档；建议登录后刷新页面。"数据照常保存，不会因为识别失败而停止采集。用户可以在归档页给这个桶改展示名（只改 `label`，不改 `accountKey`）。

内测阶段如果已经积累了一批 `default` 桶数据，公测前完成账号识别后直接清空内测数据即可，**不做自动迁移**——按 URL 猜归属比重新采集更容易出错。

#### 8.4.3 为什么不读 Cookie / localStorage

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| `chrome.cookies` 读会话 Cookie | 不采用 | 需要 `cookies` 权限；会接触登录令牌；商店审核敏感；令牌会轮换，做身份键不稳定 |
| 读页面 `localStorage` | 不采用 | 里面常混有 token；扩展没有必要碰 |
| `chrome.identity` | 不适用 | 只服务 Google OAuth，AI 站点不用这套 |
| 页面可见的账号菜单 | **采用** | 零额外权限、稳定、用户看得见，出错也容易解释 |

#### 8.4.4 各种场景下的归档位置

| 场景 | 归档到哪 | 说明 |
| --- | --- | --- |
| 两个 Chrome 配置文件各登一个号 | 两个独立数据库 | 物理隔离，最彻底 |
| 同一配置文件切换平台账号 | 同一数据库的两个账号桶 | 归档页可按账号筛选 |
| 同一账号切换工作区 | 两个桶 | 会话列表本来就不同 |
| 无痕窗口 | 不采集 | manifest 设 `incognito: "not_allowed"` |
| 共享链接被另一个账号打开 | 两个账号各一份 | 有意的取舍：宁可重复，也不混号 |
| 退出登录 | 暂停采集，不清数据 | 角标 paused，提示"等待登录" |

#### 8.4.5 多标签页 × 多账号

两个标签页分别是账号 A 和 B 时，各自的内容脚本算出不同的 `accountKey`，SW 按 `conversationId`（已含账号）分队列，互不影响。若同一标签页内切换账号，按 8.4.1 的 flush → 重建流程处理。

#### 8.4.6 对导入导出的影响

- Markdown front matter 带 `account: a***@gmail.com`；JSON 备份带 `accounts: Account[]`。
- 导入时**保留文件里的 `accountKey`**，不按本机重新计算；因此换机恢复后仍是同一个桶。
- 若本机已存在同名但不同 key 的账号（理论上只会在用户手工改过 key 时发生），导入报告里列为"疑似同账号"，由用户决定是否合并（MVP 只提示，不自动合并）。

### 9.2 逐个说明

| 权限 | 用途 | 是否必需 | 风险与说明 |
| --- | --- | --- | --- |
| `storage` | 存开关、排除站点、调试标记 | 必需 | 只读小配置，不含对话正文 |
| `unlimitedStorage` | 归档可能超过默认配额，避免被浏览器清理 | 建议 | Chrome 安装时不额外弹窗；无此权限时大归档可能写入失败 |
| `alarms` | 每日维护（统计用量、查配额） | 建议 | 不涉及页面访问；也可用 `setTimeout` 兜底，但 SW 休眠后不可靠 |
| `host_permissions`（7 条域名） | 在这些站点注入内容脚本 | 必需 | 最小集；不申请 `<all_urls>` |
| ~~`tabs`~~ | 不需要：跳转原会话用 `chrome.tabs.create({url})` 即可 | 不申请 | — |
| ~~`scripting`~~ | 不需要：用声明式 `content_scripts` 静态注入 | 不申请 | 避免"可向任意页面注入代码"的观感 |
| ~~`downloads`~~ | 不需要：归档页用 `Blob + <a download>` 导出 | 不申请 | 少一个权限，上架审核更顺 |
| ~~`webRequest`~~ | 不需要：不碰网络请求 | 不申请 | — |
| ~~`cookies`~~ | 不需要：账号识别只用页面可见的账号菜单 | 不申请 | 避免接触会话令牌，也少一个高敏感权限 |
| ~~`identity`~~ | 不需要：不做 OAuth，AI 站点也不支持 | 不申请 | — |
| ~~`<all_urls>`~~ | 不需要 | 不申请 | 明确写进商店说明，作为隐私卖点 |

**仅 Chrome**：`minimum_chrome_version` 设为 120（用到 `chrome.action` 的 Promise 形式等较新 API），不声明 Firefox / Edge 兼容，也不在 manifest 里写 `browser_specific_settings`。

**无痕模式**：`incognito: "not_allowed"` 让扩展完全不在无痕窗口运行。无痕本身就是为了不留痕迹，扩展再往里写归档既违背用户预期，也会让"账号归属"变得难以解释。

**动态域名**：Kimi / Grok 的域名可能调整。方案是把域名清单集中在 `manifest.ts` 的 `PLATFORM_HOSTS`，发版时只改一处；不做"运行时申请新域名"（会触发用户授权弹窗，MVP 不做）。

## 10. 隐私与安全

### 10.1 数据边界

- 只读目标对话页的消息区域，不读输入框草稿、不读侧边栏其他会话、不读登录凭证。
- 不采集用户名、头像、账号 ID 的**原文**；为了区分多账号，只保存账号标识的单向哈希（`accountKey`）和脱敏展示名（`a***@gmail.com`）。
- 不读取 Cookie、`localStorage`、登录令牌；账号线索只来自页面可见的账号菜单。
- 不发起任何网络请求；扩展页面 CSP 的 `connect-src 'none'` 从浏览器层面兜住。
- 不加载远程代码（MV3 本来就禁止），不引 CDN 资源，所有依赖打包进扩展。

### 10.2 用构建期规则保证"零上传"

1. ESLint 自定义规则：`src/` 下禁止 `fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`、`navigator.sendBeacon`、`importScripts`（远程 URL）。
2. CI 检查：对 `dist/*.js` 做一次文本扫描，出现上述 API 或非 `chrome-extension://` 的绝对 URL 即失败。
3. E2E 断言：跑完整流程时用 Playwright 监听 `request` 事件，除 `chrome-extension://` 与测试夹具服务器外不允许有其他请求。
4. `privacy.md` 写清楚：存什么、存哪里、不上传、如何删除、敏感信息提示。

### 10.3 HTML 消毒（必须做，不是可选项）

AI 回复里的 HTML 是**不可信输入**（模型可能输出 `<img onerror=...>`、`<script>`）。归档页若直接 `innerHTML`，等于给自己开了一个 XSS 口子，而扩展拥有更高权限，后果比普通网页更严重。

- 入库前用 DOMPurify 白名单清洗：`p, br, pre, code, ul, ol, li, blockquote, strong, em, b, i, h1-h6, table, thead, tbody, tr, th, td, a, hr`。
- 属性只留 `href`（仅 http/https）、`title`、`class`（仅允许 `language-*`、`code-block` 等白名单前缀）。
- **`<img>` 一律替换成占位链接**：避免打开归档页时向平台 CDN 发请求（既是隐私泄漏，也会让"零上传"承诺打折）。需要看图的场景，用户点"在原网页打开"。
- 渲染时再清洗一次（纵深防御），并给归档页加严格 CSP。
- 单测必须覆盖：`<script>`、`onerror`、`javascript:` 链接、`<iframe>`、`<style>`、SVG 事件属性。

### 10.4 本地数据的安全边界（如实告知用户）

IndexedDB 是扩展私有存储，其他网站读不到，但**本机上能访问浏览器用户目录的人/程序可以读到**。因此：

- 首次使用时明确提示："归档保存在本机浏览器中，可能包含敏感信息，请自行备份与清理。"
- 支持"删除单个会话""清空全部数据""暂停当前站点"。
- 不做伪加密（明文套一层 Base64 没有意义）。加密按产品决策放到后续版本（口令派生密钥 + WebCrypto AES-GCM），本期不实现。
- 账号哈希会写进导出文件：它能区分账号，但无法还原出邮箱/手机号；导出文件本身已含全部对话正文，请像对待聊天记录一样对待备份文件。

## 11. 状态、错误与可观测性

### 11.1 角标状态机

| 状态 | 角标 | 触发条件 | 弹窗文案 |
| --- | --- | --- | --- |
| unsupported | 灰色 `–` | 当前标签页不在支持域名内 | "当前站点暂不支持归档" |
| paused | 灰色 `⏸` | 全局关闭 / 本站暂停 / 在排除列表 / 等待登录信息 | "已暂停保存：<原因>" |
| active | 绿色，数字为当前会话已存条数（>99 显示 `99+`） | 正常运行且有会话 | "已保存 N 条 · 最近同步 HH:mm · 账号 a***@gmail.com" |
| syncing | 蓝色（短暂） | 正在写入 | "正在保存…" |
| degraded | 黄色 `!` | 部分消息解析失败 | "部分内容未能保存，可尝试手动同步" |
| broken | 橙色 `!` | 适配失败（消息节点为 0 或连续异常） | "当前页面无法自动保存，可手动同步或等待适配更新" |
| error | 红色 `!` | 写库失败（配额满 / DB 被锁） | "保存失败：<可读原因>，请导出备份并清理空间" |

角标按 tab 维护（`chrome.action.setBadgeText({ tabId })`），避免切标签串台。

### 11.2 错误分类与用户可见文案

| 内部错误码 | 触发场景 | 用户文案（简单话） | 技术处理 |
| --- | --- | --- | --- |
| `ADAPTER_NO_NODES` | 会话页找不到消息节点 | 当前页面无法自动保存，可手动同步或等待适配更新 | 停止自动轮询，上报诊断 |
| `ADAPTER_PARSE_PARTIAL` | 部分节点解析失败 | 部分内容未能保存 | 继续保存成功的部分，记录 misses |
| `DB_QUOTA` | 配额不足 | 本地空间不足，请导出备份后清理 | 暂停写入，角标红色 |
| `DB_BLOCKED` | 其他标签页持有旧版本连接 | 保存暂时被占用，正在重试 | 退避重试，提示刷新页面 |
| `SW_TIMEOUT` | 后台 30s 未响应 | 保存稍后重试 | 内容脚本退避重试（1s/3s/10s） |
| `PERMISSION_REVOKED` | 用户取消了站点权限 | 已失去本站权限，无法保存 | 停止注入，显示提示 |
| `IMPORT_INVALID` | 导入文件格式不对 | 备份文件无法识别 | 拒绝导入，不破坏现有数据 |
| `ACCOUNT_UNKNOWN` | 拿不到账号线索 | 未识别到登录账号，已归入默认归档 | 用 `default` 桶继续保存，不中断 |

**原则**：错误必须"可见但不打扰"——不弹 `alert`、不遮挡页面、不往控制台刷屏；用户主动打开弹窗/归档页时才看到详情。

### 11.3 调试日志

- 环形缓冲 500 条，只存元数据：时间、会话 ID 短哈希、adapter 版本、选择器 misses、耗时、错误码。
- 默认**不记录消息正文**；开启"调试模式"后才记录前 200 字符（并提示可能含敏感信息）。
- "导出诊断"生成 JSON：扩展版本、浏览器版本、平台、adapter 版本、misses、事件列表；默认不含正文，方便用户发给开发者排障。
- 日志写入走内存缓冲 + 空闲时批量落库，避免每条日志一个事务。

## 12. 搜索

### 12.1 MVP 方案（够用且简单）

- 搜索在 `search.worker.ts` 里跑，不阻塞 UI。
- 数据来源：`messages` store 游标分批读（每批 500），只读 `contentText / role / conversationId`；`conversations` 一次读入内存做标题匹配（会话数量级远小于消息）。
- 匹配规则：
  - 查询先做 NFKC + 小写 + 去零宽字符；
  - 多个关键词空格分隔，AND 语义；
  - 中文按子串匹配（不引分词器，避免包体和词典问题）；
  - 平台、账号、日期范围、角色作为过滤条件。账号筛选下拉显示脱敏展示名，默认"全部账号"。
- 结果：按会话聚合，每个会话展示命中的前 3 条 + "还有 N 条"；片段截取命中位置前后 60 字符，命中词高亮。
- 排序：标题命中优先 > 最近更新 > 命中次数。
- 限制：最多返回 200 条消息（分页加载更多），避免一次渲染爆炸。
- 点击结果：`chrome.tabs.create({ url })` 打开原会话；同时把 `conversationId + msgKey` 发给内容脚本做高亮定位（第二阶段）。

### 12.2 性能与后续演进

| 数据量 | 全量扫描耗时（估算） | 策略 |
| --- | --- | --- |
| < 1 万条 | < 150ms | 直接扫，结果缓存 30s |
| 1–5 万条 | 0.5–1.5s | 扫的时候显示进度；按会话分批出结果 |
| > 5 万条 | 明显变慢 | 第二阶段引入倒排索引（CJK 用 bigram，英文用词元），存 `searchIndex` store |

MVP 不做倒排索引：先验证"存得下、找得到"，避免过早优化。但 schema 里预留 `searchIndex` 的规划位置，迁移时新增即可。

## 13. 导出、导入与清空

> **导出策略（已确认）**：面向用户的默认导出是 **Markdown**；JSON 只作为"完整备份/恢复"格式保留。原因：Markdown 适合阅读和二次使用，但会丢字段（消息 ID、指纹、HTML），恢复必须用无损的 JSON。

### 13.1 JSON 备份格式（恢复用，非默认）

```jsonc
{
  "format": "ai-chat-archive",
  "schemaVersion": 1,
  "appVersion": "0.1.0",
  "exportedAt": "2026-10-18T12:00:00.000Z",
  "stats": { "conversations": 12, "messages": 486 },
  "accounts": [ /* Account[]，多账号档案 */ ],
  "conversations": [ /* Conversation[] */ ],
  "messages": [ /* Message[]，含 conversationId */ ]
}
```

- 导出全量或按平台/账号/日期筛选导出。
- 文件名：`ai-chat-archive-backup-2026-10-18.json`。
- 导出前估算体积，超过 50MB 时提示"建议分平台导出"。
- 入口放在设置页的"备份与恢复"，不作为首屏主按钮，避免用户误以为 JSON 是给人读的。

### 13.2 Markdown 格式（默认导出）

每个会话一个文件（批量导出时合并为一个 `.md`，用 `---` 分隔并生成目录）：

````markdown
---
platform: claude
account: a***@gmail.com
conversation_id: claude:3f9a2c81d4e6:8f3c…
title: 重构支付模块
url: https://claude.ai/chat/8f3c…
created_at: 2026-10-01T09:12:00+08:00
updated_at: 2026-10-03T18:40:00+08:00
message_count: 42
---

# 重构支付模块

## 用户
帮我看看这段代码…

## 助手
问题出在……

```ts
// 代码块保留
```
````

- 代码块语言标记从 `<pre><code class="language-xxx">` 提取。
- 图片输出为 `![图片](原URL)` 链接，不内嵌二进制。
- 文件名：`<平台>-<标题>-<日期>.md`，标题里的非法字符替换为 `-`。
- 批量导出时生成目录（TOC），按平台/账号分组。

### 13.3 导入

> 只支持导入 JSON 备份。Markdown 是阅读/交换格式，不承担无损恢复，页面上会明确提示。

1. 读文件 → 校验 `format` 与 `schemaVersion`（高于当前扩展版本直接拒绝，并提示升级）。
2. 预检（dry-run）：统计将新增/更新/跳过的数量，**先给用户看报告再确认写入**。
3. 写入：按 `conversationId` 分组，**通过 SW 的 merge 通道**（与采集同一条路径，保证去重规则一致），而不是在归档页裸 `put`。归档页始终只读，导入/清空也走协议消息。
4. 冲突策略：同一 `msgKey` 以 `updatedAt` 较新者为准；`updatedAt` 相同则保留本地。
5. 导入完成后提示：新增 X 个会话、Y 条消息；跳过 Z 条重复。

### 13.4 清空

- "清空全部数据"需输入确认词（例如输入"删除"）才执行，防止误触。
- 清空后保留设置项（开关、排除站点），删除 `conversations / messages / accounts / events / syncState`。
- 提供"删除某个平台的数据"作为中间选项。

## 14. 性能与稳定性预算

### 14.1 硬指标

| 指标 | 目标 |
| --- | --- |
| 页面额外内存 | < 30MB（内容脚本），归档页打开时 < 80MB |
| 空闲 CPU | 接近 0（无定时轮询，纯事件驱动） |
| 常规快照写入 | < 50ms（≤ 100 条） |
| 大补录（2000 条） | < 500ms，可感知但不卡顿 |
| 归档页首屏 | < 800ms（1000 个会话以内） |
| 搜索（1 万条） | < 300ms |
| 单次提取 DOM 扫描 | < 20ms（≤ 200 节点） |

### 14.2 节流参数（集中在 `shared/constants.ts`）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 消息变化防抖 | 800ms | 合并同一轮渲染的多条 DOM 变更 |
| 流式写入节流 | 1500ms / 变化 ≥ 20 字符 | 草稿不刷库 |
| 完成判定静默期 | 1200ms | 文本稳定后才置 complete |
| 滚动监听节流 | 250ms | 触发补录，另有 1s 冷却 |
| 标题防抖 | 800ms | 避免生成中标题抖动 |
| 单事务批量 | 200 条 | 控制事务时长 |
| 对齐上限 | 4000 条 | 超出退化为尾窗 diff |
| 重试退避 | 1s / 3s / 10s，最多 3 次 | SW 无响应时 |

### 14.3 稳定性措施

- `MutationObserver` 只观察消息容器；容器重建（SPA 切换）时重新绑定，用 `WeakRef` 防止泄漏。
- 同一页面只允许一个内容脚本实例（`window.__AI_ARCHIVE_LOADED__` 守卫），避免扩展重载后重复注入。
- 所有 DOM 读取包 `try/catch`，单条消息解析失败不影响整批。
- 写库失败不丢数据：`syncState` 记录待重试快照的哈希；内容脚本保留下一次快照即可自然重试。
- 页面卸载前 flush 草稿（`pagehide` + `visibilitychange`）。

### 15.2 MVP 范围（第一版发什么）

- DeepSeek + Claude 两个平台（一个国内、一个海外，验证适配器抽象是否成立）。

| E09 | 排除站点 | 把当前域名加入排除 | 停止注入/停止写入，角标 paused |
| E10 | 多标签页 | 两个标签页同会话各发一条 | 合并正确，无重复 |
| E11 | 适配失败 | 移除消息节点 | 角标 broken，网页仍可正常输入 |
| E12 | 零网络 | 监听所有请求 | 只有 `chrome-extension://` 与夹具本地请求 |
| E13 | 账号切换 | 同一标签页从账号 A 切到 B 后继续对话 | 生成两个账号桶；A 的会话不被改动；弹窗账号名更新 |
| E14 | 无痕不采集 | 尝试在无痕窗口打开 | 扩展不运行，不产生任何归档（manifest 限制） |

## 17. 风险与决策记录

### 17.1 风险清单

| 风险 | 可能性 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 平台 DOM 改版导致选择器失效 | 高 | 采集失败 | 适配器隔离 + 自检 + 角标提示 + 手动同步 + 快速发版流程 |
| 哈希 class 变化频繁 | 高 | 解析失败 | 优先语义属性；哈希选择器只做兜底并标注 |
| 虚拟列表导致历史采不全 | 中 | 归档不完整 | 滚动增量采集 + 提示继续滚动，不承诺全量 |
| SW 被休眠打断写入 | 中 | 单次失败 | 幂等 + 重试 + 事务原子性 |
| 多标签页并发 | 中 | 重复/覆盖 | 单写者 + 串行队列 + 唯一索引 |
| 账号识别失败或误判 | 中 | 数据分桶错误 | 默认桶兜底 + 状态提示 + 归档页可改展示名；P0 先验证各平台账号线索 |
| 长会话性能 | 中 | 卡顿 | 对齐上限、分块事务、Worker 搜索 |
| 归档页 XSS | 低 | 高风险 | 入库与渲染双重消毒 + CSP + 单测 |
| 本地磁盘被清理 | 低 | 数据丢失 | unlimitedStorage + 容量告警 + 导出提醒 |
| 平台条款/合规 | 中 | 下架风险 | 只读、仅本地、不绕过付费；商店说明写清用途 |

### 17.2 已确认的产品决策（2026-10-18）

| # | 问题 | 决定 | 对方案的影响 |
| --- | --- | --- | --- |
| 1 | 浏览器 | 只做 Chrome 桌面版；Firefox、Edge 不测试、不适配 | manifest 只声明 Chrome；`minimum_chrome_version: 120`；不写 `browser_specific_settings` |
| 2 | 归档范围 | 只存用户与助手的可见文本和代码块 | 不采集 system/tool、Artifacts；消毒白名单只保留基础排版 |
| 3 | 图片/附件 | 只存 URL 与文件名，不下载本体 | `attachments` 只留 `url/name`；`<img>` 转占位链接；后续版本再加"保存副本/下载链接"选项 |
| 4 | 加密 | 本期不做，放到以后 | 明文存 IndexedDB，靠系统磁盘加密 + 首次使用提示；不做伪加密 |
| 5 | 保留期限 | 永久保存，不自动清理 | 去掉保留期清理任务，只保留容量告警与手动删除 |
| 6 | 多账号 | 必须处理：账号指纹分桶 + Chrome 配置文件隔离 | 会话主键含 `accountKey`；新增 `accounts` store；见 §8.4 |
| 7 | 导出格式 | 当前版本以 Markdown 为准 | Markdown 为默认导出；JSON 仅作无损备份/恢复；不做 Obsidian/Notion 专用格式 |
| 8 | 归档内继续对话 | 不做，只归档 | 归档页只读，不提供输入框 |

### 17.3 仍待 P0 实测确认的技术细节（不阻塞开工）

1. 各平台账号菜单的真实 DOM 与可用线索（邮箱 / 用户 ID / 工作区名）——决定 `getAccountHint` 的写法，实测后回填 §4.4 的表。
2. 各平台会话 ID 在"分享链接、跨工作区、切换账号后"是否仍然稳定。
3. `minimum_chrome_version` 是否可以从 120 下调（取决于最终用到的 API）。
4. 多账号识别失败时的默认桶命名与提示文案（"默认账号"还是"未识别账号"）。

## 附录 B：术语表（给非技术同学）

| 术语 | 大白话 |
| --- | --- |
| 适配器（adapter） | 每个网站一个"翻译官"，负责看懂那个网站的页面结构 |
| 内容脚本（content script） | 注入到网页里、只读页面内容的小程序 |
| Service Worker | 扩展的后台小程序，负责统一写数据库 |
| IndexedDB | 浏览器自带的本地数据库，存在你电脑上 |
| 指纹（fingerprint） | 根据内容算出的短编码，用来判断"是不是同一条消息" |
| 幂等 | 同一件事做多少遍，结果都一样（不会重复插入） |
| 虚拟列表 | 网页只渲染屏幕附近的几条，滚动时才创建新的，所以抓不全 |
| 防抖 / 节流 | 防抖 = 等安静下来再做；节流 = 一段时间最多做一次 |
| 迁移（migration） | 扩展升级时，把旧数据整理成新格式，保证不丢 |
| 账号指纹（accountKey） | 根据账号标识算出的短编码，用来把不同账号的数据分开放 |
| Chrome 配置文件（Profile） | Chrome 里独立的一套浏览器身份，各自有独立的扩展数据 |
